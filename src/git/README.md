# Mini Git

A small Git implementation written from scratch in Rust.

This project was built as a learning exercise to understand how Git works internally rather than simply using its high-level commands. The implementation focuses on Git's object model, object storage, hashing, compression, trees, and commits.

The main goal was compatibility: objects created by Mini Git should be readable and valid according to the real Git implementation.

## Features

The following commands are currently supported:

```bash
git init
git hash-object
git cat-file
git write-tree
git commit-tree
```

### `git init`

Creates a minimal Git repository, including the required `.git` structure:

```text
.git/
├── HEAD
├── config
├── description
├── hooks/
├── info/
│   └── exclude
├── objects/
│   ├── info/
│   └── pack/
└── refs/
    ├── heads/
    └── tags/
```

The repository can be recognized and inspected by the real Git CLI.

### `git hash-object`

Creates Git-compatible blob objects.

```bash
./rust-execises git hash-object -w file.txt -C /path/to/repository
```

The implementation:

- Reads the file contents
- Builds the Git object header
- Calculates the SHA-1 object ID
- Compresses the object using zlib
- Stores it under `.git/objects`

Objects generated by Mini Git can be inspected using:

```bash
git cat-file -p <hash>
```

### `git cat-file`

Reads and inspects loose Git objects.

Supported operations include:

```bash
git cat-file -p <hash>
git cat-file -t <hash>
git cat-file -s <hash>
git cat-file -e <hash>
```

This required implementing:

- Object lookup
- SHA prefix resolution
- zlib decompression
- Git object header parsing
- Blob, tree, and commit inspection

### `git write-tree`

Recursively converts the working directory into Git tree objects.

```bash
./rust-execises git write-tree -C /path/to/repository
```

The implementation:

- Recursively traverses directories
- Ignores `.git`
- Creates blob objects for files
- Creates nested tree objects for directories
- Preserves regular and executable file modes
- Produces deterministic tree objects
- Stores SHA-1 references using Git's binary 20-byte representation

Example structure:

```text
repository
├── README.md
├── run.sh
└── src
    ├── main.rs
    └── utils
        └── helper.rs
```

Conceptually becomes:

```text
root tree
├── blob README.md
├── blob run.sh
└── tree src
    ├── blob main.rs
    └── tree utils
        └── blob helper.rs
```

Changing a deeply nested file changes its blob hash, which changes its parent tree hash and eventually propagates to the root tree hash.

### `git commit-tree`

Creates Git-compatible commit objects.

```bash
./rust-execises git commit-tree <tree-hash> \
    -m "Initial commit" \
    -C /path/to/repository
```

Commits can also reference a parent:

```bash
./rust-execises git commit-tree <tree-hash> \
    -p <parent-commit-hash> \
    -m "Second commit" \
    -C /path/to/repository
```

The resulting commit contains:

```text
tree <tree-hash>
parent <parent-hash>
author ...
committer ...

Commit message
```

The parent is optional, allowing the creation of an initial commit.

## Git Object Model

One of the main goals of the project was understanding Git's content-addressable object database.

The implemented model can be summarized as:

```text
files
  │
  ▼
blob objects
  │
  ▼
tree objects
  │
  ▼
commit objects
  │
  ▼
parent commits
```

Every object is identified by a SHA-1 derived from its contents.

For example, a blob is hashed from:

```text
blob <size>\0<content>
```

A tree contains entries referencing blobs and other trees.

A commit references a root tree and optionally one or more previous commits.

This means changing a file can propagate through the complete object graph:

```text
file changes
    ↓
blob hash changes
    ↓
tree hash changes
    ↓
parent tree hash changes
    ↓
root tree hash changes
    ↓
commit hash changes
```

## Compatibility With Git

A major requirement of this project was that Mini Git should not use a custom representation.

The generated objects use the actual Git object format.

They are validated using the real Git CLI:

```bash
git cat-file -p <hash>
git cat-file -t <hash>
git cat-file -s <hash>
git fsck --full
```

For example:

```bash
TREE=$(./rust-execises git write-tree -C /tmp/repository)

git -C /tmp/repository cat-file -t "$TREE"
```

returns:

```text
tree
```

Git can also recursively inspect the blobs and nested trees created by Mini Git.

## End-to-End Tests

The project includes an E2E test suite written in Rust.

The tests execute the actual Mini Git binary and use the real Git implementation as a reference.

Run them with:

```bash
cargo test
```

The suite is organized by command:

```text
test_e2e_git
├── init
├── hash_object
├── cat_file
├── write_tree
└── commit_tree
```

The tests verify properties such as:

- Repository compatibility with Git
- SHA-1 equality with `git hash-object`
- Object readability using `git cat-file`
- Correct object types
- Correct object sizes
- Tree file modes
- Executable file handling
- Empty blobs
- Deterministic tree generation
- Nested tree hash propagation
- Commit parent relationships
- Object integrity using `git fsck`

This makes the real Git implementation the compatibility reference for the project.

## What I Learned

This project was primarily about understanding systems concepts rather than recreating every Git command.

Some of the main topics explored were:

- Content-addressable storage
- SHA-1 hashing
- zlib compression and decompression
- Binary serialization
- Hexadecimal vs binary hash representations
- Recursive filesystem traversal
- Unix file modes
- Deterministic serialization
- Git's object database
- Blob objects
- Tree objects
- Commit objects
- Parent-based history
- CLI design
- Error handling in Rust
- End-to-end testing
- Compatibility testing against an existing implementation

One particularly interesting detail was that Git tree objects do not store referenced SHA-1 values as their 40-character hexadecimal representation.

Instead, each tree entry stores the raw 20-byte SHA-1 value:

```text
<mode> <filename>\0<20-byte SHA-1>
```

Understanding details like this was one of the main reasons for implementing the project from scratch.

## Scope

Mini Git is intentionally not intended to replace Git.

Several major Git features are not implemented, including:

- Index / staging area
- `git add`
- Branch manipulation
- Ref updates
- `git status`
- `git checkout`
- `git log`
- Packfiles
- Remote repositories
- Fetch / push
- Merge algorithms

The project stops after implementing the fundamental Git object model because its purpose is educational: understanding how Git represents files, directories, and history internally.

## Building

```bash
cargo build --release
```

The resulting executable will be available at:

```bash
./target/release/rust-execises
```

## Running

For example:

```bash
./target/release/rust-execises git init /tmp/my-repo

echo "Hello World!" > /tmp/my-repo/hello.txt

./target/release/rust-execises git hash-object \
    -w /tmp/my-repo/hello.txt \
    -C /tmp/my-repo

./target/release/rust-execises git write-tree \
    -C /tmp/my-repo
```

The generated objects can then be inspected directly using the real Git CLI.

## Purpose

This project is part of my process of learning Rust through practical systems programming projects.

Rather than attempting to build a production-ready Git implementation, the objective was to reproduce enough of Git's internals to understand the concepts behind its object database and verify the implementation against Git itself.
